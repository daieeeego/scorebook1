## 1. 背景と目的

### 1.1 現状
- 少年野球チームのスコアは紙のスコアブックで運用している。
- 印刷された紙が正（原本）として保管・共有されている。
- 共有は記入済みページを写真に撮り、LINE で送っている。
- 集計欄（打率・投球数・チーム打撃率など）は試合後に手計算している。

### 1.2 課題
- **記録者によって書き方が揃わない。** 補殺・刺殺・失策の欄は埋める人と埋めない人がいる。判断に迷うプレー（失策か野選か、盗塁か暴投か捕逸か）の扱いが人によって異なる。
- 野球経験の少ない保護者が記録係に入ると、記録の質が大きく落ちる。
- 集計が手計算のため手間がかかり、間違いも起きる。
- 過去データが紙に閉じているため、傾向分析や対戦相手の対策に使えない。

### 1.3 目的
**誰が入力しても同じ品質・同じ表記の記録が残ること。**

成績集計の自動化はその副産物であり、主目的ではない。入力を正規化するためにルールエンジンを持つ、というのが本システムの中核方針である。

### 1.4 副次的な目的
- 投球数・出場イニングを試合中に可視化する
- 集計欄の自動算出により試合後の手計算をなくす
- 打球方向・配球・起用の傾向を後から分析できるようにする
- 対戦相手のデータを蓄積し、次回対戦時の対策に使う

## 2. 成功条件

| ID | 条件 |
|---|---|
| SC-01 | 野球経験の浅い保護者が、事前レクチャーなしで1試合を最後まで記録し切れる |
| SC-02 | 記録者が変わっても、同じ試合なら同じ記録になる |
| SC-03 | 出力したスコアブックが、現行の紙と同じ様式で印刷でき、そのまま保管できる |
| SC-04 | 1プレーあたりの入力が3タップ以内で完了する |
| SC-05 | 試合中に通信が切れても記録が継続でき、データが失われない |

SC-04 の測定のため、**タップ数の計測機能を試作に組み込んでいる**（画面上部に「タップ数 / プレー」を常時表示）。取り消し操作もタップとして計上する。押し間違いは実際に発生するコストであり、それを除外した数字では現場の負荷を測れないため。

**選手交代の画面での操作は計測に含めない。** 交代は「1プレーの入力」ではなく、イニングの合間に行う別種の作業であり、混ぜるとプレーあたりの負荷が読めなくなるため。

## 3. 利用者と利用シーン

### 3.1 利用者
| 役割 | 想定 | 備考 |
|---|---|---|
| 記録係 | チームの誰でも（保護者・コーチ） | 野球知識のばらつきを前提とする。毎試合同じ人とは限らない |
| ベンチ（監督・コーチ） | 投球数・出場イニングの確認 | 入力はしない。画面を覗く |
| 分析者 | 試合後の振り返り | 現状は限られた人 |

### 3.2 利用シーン
- **試合中**：グラウンドのベンチ。スマホまたはタブレット1台で入力。通信環境は不安定または圏外。屋外のため画面が見づらく、片手操作になることもある。
- **試合直後**：スコアブックを印刷・PDF化して共有。
- **後日**：蓄積データから傾向を確認。

### 3.3 端末
- 入力：スマートフォン（最小幅375px想定）／タブレット
- 閲覧・修正：タブレット／PC
- **入力と閲覧で必要な画面が異なる。** スコアブック全面（27打席×2チーム）の俯瞰はスマホでは成立しないため、入力画面のみスマホ最適化し、俯瞰・修正画面はタブレット以上を前提とする。

## 4. スコープ

### 4.1 Phase 1（試作・実戦フィードバック取得）

**実装済み**
- 試合設定（日付・球場・チーム名・打順9人の背番号・守備位置）
- 1球ごとの投球結果入力（ボール／ストライク／ファウル）
- 打球方向の入力（守備位置9箇所のタップ）
- 打席結果の入力（全ゾーン共通の固定選択肢）

- **保留プレーの確定（試合後に一覧から結果を決める）**
- 選択1つ単位での取り消し（確定後も段階的に戻る）
- **選手交代・代打・代走・守備位置変更と、その履歴の表示**
- 投球数（**投手ごと**）・イニング・アウト・走者・カウント・打者の常時表示
- **出場イニング数の確認画面**
- 自動保存（localStorage、1操作ごと）
- JSON エクスポート／**インポート**、**旧形式データの自動移行**
- PWA（ホーム画面追加、オフライン動作）
- タップ数の計測表示

**未実装（Phase 1 の残作業）**
- なし。**次にやるのは機能追加ではなく、自分で1試合を通しで入力すること**（11章）。

### 4.2 Phase 2
- スコアブック様式の印刷出力（SVG）
- PDF／PNG 出力と共有
- サーバ同期と選手マスタ・相手チームマスタの共有
- リエントリー（再出場）と RuleConfig（連盟差の設定値）
- 分析画面（打球方向、配球傾向、打順・起用の検証、対戦相手の傾向）

### 4.3 Phase 3 以降（未定）
- 個人成績の通年集計
- 複数端末からの同時入力
- 球種・コースの記録
- ダブルスチール（複数走者の同時進塁）の一括入力

### 4.4 やらないこと
| 項目 | 理由 |
|---|---|
| 球種の記録 | 学童では変化球がほぼなく、判別も記録者によってブレる |
| 投球コース（9分割） | 1球あたり1タップ増となり、リアルタイム入力の負荷が跳ね上がる |
| 試合中のリアルタイム複数端末同期 | 同時入力の要件がない。試合後同期で足りる |
| 投球数制限の警告通知 | 画面で見えれば十分との判断 |
| 選手氏名の登録 | 端末に個人情報を残さないため。背番号のみで運用する |
| 自由記述による記録 | 表記ゆれの原因そのもの。ただし保留のメモは例外（下記 5.1 参照） |

凡例：**済** = 試作に実装済み / **未** = 未実装

### 5.1 記録
| ID | 要件 | 状態 |
|---|---|---|
| FR-01 | 1球ごとに投球結果（ボール／ストライク／ファウル）を記録できる | 済 |
| FR-02 | 打席結果を、あらかじめ定義された選択肢から選んで記録できる | 済 |
| FR-03 | 打球方向を守備位置のタップで記録できる | 済 |
| FR-04 | 走者の進塁はシステムが導出し、複数の解釈があり得る場合のみ利用者に問う | 済 |
| FR-05 | 判断がつかないプレーを「保留」として記録し、試合を止めずに進行できる | 済 |
| FR-06 | 保留したプレーにメモを残せる。定型文のタップと自由記述の両方に対応し、空でも記録できる | 済 |
| FR-07 | 走者単独のプレー（盗塁・暴投・捕逸・けん制）を、理由を選択して記録できる | 済 |
| FR-08 | 保留した記録を試合後に一覧から確定できる | 済 |
| FR-09 | 選手交代・守備位置変更・代打・代走を記録できる | 済 |
| FR-10 | 1プレーごとに自動保存され、アプリが落ちても復帰できる | 済 |
| FR-31 | 交代の種類（代打・代走・守備交代）は場面から自動で決まり、利用者は選ばない | 済 |

**FR-06 の補足**：保留のメモだけは自由記述を許す。集計対象ではなく、記録者が後から思い出すための材料であるため、表記ゆれの排除という原則の対象外とする。

**FR-08 の補足**：確定しても過去のイベントは書き換えない。確定は追記イベントとして持ち、再生時に差し替える（6.3）。確定するとその打席以降の盤面（アウト・走者・得点）が自動で計算し直される。確定自体も「1つ戻す」で取り消せる。

**FR-31 の補足**：その選手が塁上にいれば代走、打席に立っていれば代打、それ以外は守備交代として記録する。判定材料は盤面にあり、記録者に聞く必要がない（7.1 第2層）。

### 5.2 取り消し
| ID | 要件 | 状態 |
|---|---|---|
| FR-11 | 取り消しは「選択1つ」単位で動作する。打席が確定した後でも、直前の選択画面に戻る形で1つずつ剥がせる | 済 |
| FR-12 | 取り消しボタンには、押す前に戻り先が表示される | 済 |
| FR-36 | 過去の打席を、その1件だけ訂正できる | **未** |
| FR-37 | 記録の行を選んで、そこから後をまとめて取り消せる | 済 |

**設計の経緯**：打席結果は「打球方向・結果・質問の答え」の3選択を1イベントにまとめて保存している。イベント削除だけで実装すると打席がまるごと消え、利用者の感覚（1操作＝1タップ）とずれる。データ構造は変えず、取り消し時に入力途中の状態を復元することで解決した。イベントを分割しない理由は、「打球方向だけ記録されて結果がない」中途半端なイベントを保存させないため。

交代と保留の確定もイベントであるため、同じ「1つ戻す」で取り消せる。

#### FR-36 の補足 ─ 途中の打席を訂正できない（実戦で顕在化）

**取り消しはあっても、訂正がない。** 「1つ戻す」は直前の1操作から順に剥がすことしかできず、
数打席前の誤りに気づいても、そこまでの操作をすべて取り消して入れ直すしかない。

初回の実戦記録では、これが実際に問題になった。**誤ったまま先へ進むしかなく、
以降の記録が手書きとずれ続けた。**

**紙との差はここにある。** 紙は該当のマスだけ消して書き直せ、前後のマスに影響しない。
アプリは1本のイベント列であり、途中を変えると以降が再計算される。再計算自体は正しい
（§6.1 の利点そのもの）が、**訂正する手段が用意されていない。**

##### 方式の候補

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 訂正イベントの追記** | `{ t:"amend", target, ... }` を追記し、再生時に対象イベントを差し替える | **推奨。** 保留の確定（FR-08）で同じ仕組みが動いており、§6.1（追記のみ）を壊さない |
| B. イベント列の直接編集 | 該当イベントを書き換える | 単純だが追記のみの前提が崩れ、Phase 2 の同期で競合が起きる |
| C. 打席の入れ直し | 対象の打席を削除して入力し直す | イベントの位置がずれ、以降の参照（保留の確定など）が壊れる |

**A は既に実績がある。** 保留の確定は `resolve` イベントを追記し、`resolvedEvents()` が
再生用の列を作って差し替えている。これを「結果の確定」から「任意の内容の訂正」へ
一般化すればよい。

##### 必要になるもの

- **打席単位の一覧**（訂正の対象を選ぶ画面）。現在のログは1操作ごとの行であり、打席単位ではない
- **選んだ打席の入力をやり直す導線**（打球方向 → 結果 → 走者の行き先）
- **訂正済みであることの表示。** 紙は二重線で消した跡が残る。どちらが正かが分かる必要がある

##### 注意すべき副作用

**訂正すると以降の盤面が変わるため、後続のイベントが成立しなくなることがある。**
たとえば訂正によって走者が塁上から消えると、その走者の盗塁イベントが宙に浮く。
再生時に成立しないイベントを検出し、記録者に知らせる仕組みが要る。

現在の `applyEvent` は、走者のいない塁に対する走者イベントを黙って無視している
（`if (runner == null) return s;`）。**黙って無視するのは訂正機能とは相性が悪い。**

## 6. ドメインモデル

### 6.1 中核方針
**盤面の状態を保存せず、プレーイベントを追記のみで積み上げ、状態は畳み込みで導出する。**

この設計により以下が成立する。
- 取り消しがイベント1件の削除で済む
- ルールを修正した後、過去試合を再生して結果を再計算できる
- 同期時の競合がほぼ発生しない（過去を書き換えないため）

### 6.2 実装形

```
Setup
  ├─ date, venue
  ├─ teamName: { away, home }
  └─ lineup:   { away: LineupSlot[9], home: LineupSlot[9] }

LineupSlot  { order: 1..9, entries: LineupEntry[] }      // 人数制限なし
LineupEntry { playerId, position, entryType, enteredAtSeq, exitedAtSeq }
             entryType: 先発 | 代打 | 代走 | 守備交代 | リエントリー
             position:  1..9 | null（守備につかない）
             exitedAtSeq が null の1件が、その枠でいま出場している選手

playerId は "away#12" の形。氏名を持たないため、
背番号がそのままチーム内の識別子になる。

PlayEvent（4種）
  ├─ { t:"pitch",   r:"ボール"|"ストライク"|"ファウル" }
  ├─ { t:"runner",  from, reason, out }
  ├─ { t:"inplay",  zone, result, answer?, note? }
  ├─ { t:"sub",     side, order, kind, num, position, base? }
  └─ { t:"sub",     side, kind:"守備位置変更", moves:[{order, position}] }

確定イベント（保留の解決。過去を書き換えないための追記）
  └─ { t:"resolve", target, result, answer? }   // target = 保留イベントの位置

GameState（導出結果・保存しない）
  ├─ inning, isTop, outs, bases[3], balls, strikes
  ├─ order{away,home}, score{away,home}
  ├─ lineup{away,home}          // 交代を反映した現在形
  ├─ pitchCount{playerId}       // 投手別の投球数（FR-19）
  ├─ halves{playerId}           // 出場したハーフイニング（FR-21）
  ├─ plateAppearances{playerId}
  └─ log[]                      // { seq, src, inning, isTop, text, kind, pending }
```

`bases[]` には背番号ではなく playerId を持つ。代走で走者が入れ替わったとき、塁上の走者そのものを差し替えるため。

### 6.3 保留の確定をどう表現するか

確定したい打席は既に過去のイベントであり、そこを直接書き換えると 6.1 の前提（追記のみ）が崩れる。同期時の競合が起き、取り消しも成立しなくなる。

そこで**確定は追記イベント（`resolve`）として持ち、畳み込みの直前に「保留」を確定内容へ差し替えた列を作って再生する**。

```
events:  [... , {t:"inplay", result:"保留"}, ... , {t:"resolve", target:12, result:"ゴロアウト"}]
              ↓ resolvedEvents()（再生用の列を作るだけ。events は変えない）
再生列:  [... , {t:"inplay", result:"ゴロアウト"}, ... ]
```

保存されるイベント列は保留のまま残る。**「あの打席は保留だった」という事実自体が記録であり、後から消してよいものではない。**

### 6.4 Phase 2 で拡張が必要な部分
- **RuleConfig**（7.2）。リエントリーの可否・投球数上限など、連盟差を試合ごとの設定として持つ。
- **選手マスタ**（FR-15/16）。現在は試合ごとに背番号を入力している。playerId をチーム単位のマスタ参照に変える。
- **fielders**（6-4-3 のような守備側の関与順）。補殺・刺殺の自動記録（8.2 の投手成績表）に必要。

### 6.5 導出関数
```js
initialState(setup) -> state
applyEvent(state, event) -> state          // 純粋関数。state は変更しない
resolvedEvents(events) -> events           // resolve を反映した再生用の列
deriveState(events, setup) -> state        // 畳み込み
stateBefore(events, setup, index) -> state // index 直前の盤面（保留の確定に使う）
questionFor(state, zone, result) -> 質問 | null
validateSub(state, sub) -> 理由 | null     // 不正な交代を止める
inferSubKind(state, side, order) -> 種類   // 代打／代走／守備交代の自動判定
statsFrom(state) -> 集計                   // 投手別投球数・出場イニング
migrate(saved) -> { setup, events, migrated }
```

これらは `src/rules.js` に UI から独立して配置している。UIを介さず単体テストできることを設計上の必須要件とする（10.2）。

## 7. ルールエンジン

### 7.1 3層構造

**第1層：制約（不正な盤面を作らせない）**

原則は「選択肢を出さないこと」で実現する。実装例：一塁と二塁の両方に走者がいる状態で安打が出た場合、二塁走者は押し出されるため「二塁に留まった」を選択肢から外す。表示すれば二塁に走者2人という不正な盤面が作れてしまう。

交代だけは背番号を自由入力するため、選択肢では防げない。`validateSub` で以下を拒否する。

- 空の背番号
- 他の打順枠で出場中の選手
- 同じ選手への交代
- 走者のいない塁への代走
- 一度退いた選手の再出場（リエントリーは Phase 2）

**第2層：導出（システムが自動で決める）**
- 四球時の押し出し進塁
- 打者走者の一塁到達
- 三塁走者の生還
- 三振・四球によるアウトカウントと打者交代
- 3アウトでのイニング交代
- **交代の種類（代打・代走・守備交代）の判定**
- **投球数を、その時点で守備位置1にいる選手へ紐づけること**
- **同じ守備位置に2人が立たないよう、先にいた選手の守備位置を外すこと**
- 補殺・刺殺・失策の記録（Phase 2）
- 打点、犠打・犠飛の成立判定（Phase 2）

**第3層：質問（必ず選択肢で問う）**

記録の揺れを吸収する本体。実装済みの質問：

| 状況 | 質問 | 選択肢 |
|---|---|---|
| ゴロアウト・一塁に走者・2アウト未満 | 一塁にいた走者はどうなりましたか | フォースアウト（二塁）／ダブルプレー／二塁へ進んだ／一塁に留まった |
| 安打または失策で出塁・二塁に走者 | 二塁にいた走者はどこまで進みましたか | （二塁に留まった）／三塁で止まった／本塁まで進んだ |
| 走者が動いた | 動いた理由は | 盗塁／ワイルドピッチ／パスボール／けん制の悪送球／盗塁アウト／けん制でタッチアウト |

走者が1人だけの場合は走者の選択を省略し、2タップで完了する。

保留を確定するときも、**その打席時点の盤面**（`stateBefore`）で同じ質問を出す。確定は試合後に行うため、現在の盤面で問うと答えが変わってしまう。

### 7.2 設定値（RuleConfig、Phase 2）
連盟によって異なるため、ハードコードせず試合ごとの設定として保持する。

- 振り逃げの採用可否
- リエントリー（再出場）の可否と回数
- 1試合／1日／1週間の投球数上限
- 規定イニング数、コールド条件、時間制限
- タイブレークの採用有無と方式

全軟連の学童部では、投球数制限が**1試合かつ1日70球以内（4年生以下は60球以内）**、
2026年シーズンより**1週間210球以内（4年生以下は180球以内）**と定められている。
上限が学年で変わるため、学年を保持しないと自動判定できない（OPEN-15）。

規定との照合結果は `ルール照合_全軟連学童部.md` にまとめた。**再出場とタイブレークの
2つは、起きた瞬間に記録が止まる種類の欠落**であり、実戦投入前に判断が要る。

## 8. 出力設計

### 8.1 単一SVGからの派生
スコアブック1枚を SVG として生成し、そこから全出力を派生させる。実装は「スコアブックSVGレンダラ」1つで足りる。

| 用途 | 実現方法 |
|---|---|
| 印刷 | SVG を A4 でブラウザ印刷 |
| LINE共有 | SVG を PNG 化（現行の写真共有と同じ使い勝手） |
| PDF | 同じ SVG を埋め込み |
| アプリ内閲覧 | 分析用に別レイアウト（縦スクロール） |

### 8.2 様式
使用中のスコアブックは**成美堂スポーツ出版の様式**。品番は9106（野球スコアブック 保存版、A4判バインダー式）と推定しているが、**現物の写真がリング綴じに見えるため別品番の可能性がある。原本での確認が必要**。ただし罫線様式は成美堂の共通フォーマットのため、再現作業への影響は小さい。

構造（写真から読み取り）：
- 打者ブロックは3行1組×9枠
- 各イニングのセルは「左の細い帯＝投球結果」＋「ダイヤモンド図＋結果記号」
- 左端に補殺／刺殺／失策の3列、その右に守備位置・氏名・打撃率・打方
- 右端に打席数・打数・得点・安打・打点・犠打・四死球・盗塁・三振・残塁
- 最下部にイニング別の得点・安打・敵失・打数・犠打・四死球・盗塁・三振・投球数
- 投手成績表（勝負・セーブ・投球回数・打者・打数・投球数・安打・本塁打・犠打・犠飛・四球・死球・三振・暴投・ボーク・失点・自責点・防御率）と捕手欄
- イニングは13回まで

**投手成績表の項目が、記録すべきイベント種別の仕様書になっている。** 自責点・暴投・ボーク・打撃妨害まで欄がある以上、扱うべき事象はこの表から逆算できる。

### 8.3 バインダー式であることの利点
A4差し替え式なら、アプリで印刷した紙をそのまま現行の原本に綴じ込める。「紙が正」という運用を壊さずに移行できる。

用紙の扱いは2案あるが、**罫線ごと白紙A4に印刷する案を採る**。市販の補充用紙（品番9107）に記入内容だけ重ね刷りする案は、プリンタの給紙誤差でずれるため実運用に耐えない。

### 8.4 印刷レイアウト上の課題
紙は1打順枠あたり3行しかないが、実運用では足りないことがある。内部データは人数無制限で保持し（FR-17）、印刷時に3行へ収める。4人目以降は注記番号を振り欄外に送る。

### 8.5 記法のマッピング
- イベントは標準形で保存し、印刷時にチームの記法へ変換する。
- **この考え方は試作で先行して適用済み**。結果の選択肢は「記録上の名称（k）」と「画面表示（l）」を分離して保持している（例：k="野手選択" / l="走者がアウト・打者は一塁へ"）。同じ仕組みを印刷時の記号変換に使う。
- **変換先の記法は `記法規約.md` に定義した**（原本の写真は `記法規約_原本.jpg`）。OPEN-01 はこれで解決。
- **ただし、現在の試作が持つイベントの粒度では規約を満たせない。** 投球結果（見逃し／空振り／ファール方向）、守備の関与順、エラーの種別、犠打・犠飛、フォースアウトとタッチアウトの区別などが不足している。差分は `記法規約.md` §13、決めるべき論点は同 §14 にまとめた。**FR-23〜FR-26 に着手する前に §14 を確定させること。**

### 8.6 個人情報
- 選手氏名は登録しない。背番号のみで運用する。
- 記録は端末内（localStorage）にのみ保存し、外部に送信しない。
- 印刷時に氏名欄をどう扱うかは未決（OPEN-05）。

## 10. 技術構成

### 10.1 Phase 1（確定・実装済み）
- Vite + React 18 + JavaScript
- 状態管理は React の useState のみ。**実行時の外部ライブラリなし**
- 永続化は localStorage（Phase 2 で IndexedDB へ移行を検討）
- vite-plugin-pwa（オフライン動作、ホーム画面追加）
- vite-plugin-singlefile（JS/CSSを index.html に全て埋め込む）

`vite-plugin-singlefile` を使う理由は、ビルド成果物がフォルダ階層を持たない6ファイルになり、**PCなしでもスマホだけで公開作業が完結する**ため。

```
src/rules.js   ルールエンジン（純粋関数。UI・DOM に依存しない）
src/App.jsx    画面
test/          ルールエンジンのテスト
```

### 10.2 テストと検証の分担

| 担当 | 範囲 |
|---|---|
| 実装者（Claude） | 要件定義、`src/` の実装、テストが落ちた箇所の修正 |
| 検証者（Codex） | `test/` の作成。**仕様書のみを根拠とし、実装は見ない** |
| Stryker | テストの assert が緩くないかを機械的に測る |

**実装者にテストを書かせない。** 実装者が書くと、仕様ではなく実装の分岐をなぞるテストになる。実装者が仕様を誤解していた場合、その誤解ごと追認されて検証にならない。

テスト対象は `src/rules.js` のみとする。純粋関数だけで構成され React も DOM も介在しないため `environment: "node"` で完結し、品質リスクもほぼこの1ファイルに集中している。`src/App.jsx` は Phase 1 では手動確認とする。

```bash
npm test          # 1回実行（vitest）
npm run mutate    # ミューテーションテスト（rules.js のみ）
```

CI（`.github/workflows/ci.yml` と `deploy.yml`）の両方で `npm test` を通す。**テストが落ちると GitHub Pages へ公開されない。** 詳細は `テスト方針_Codex連携.md`。

### 10.3 配布方法（確定・運用中）
- GitHub リポジトリ（Public）
- GitHub Actions による自動ビルド（`.github/workflows/deploy.yml`）
- GitHub Pages で公開。Pages の Source は **GitHub Actions** を指定する
- `main` への push で自動的に公開URLが更新される
- `dist` は Git 管理外。ビルド結果をコミットすると履歴が読めなくなるため
- 利用者はURLを開いて「ホーム画面に追加」

`main` は常に動作する状態を保つ。試合中に壊れたものが配信されると記録が取れなくなるため、機能追加は作業ブランチで行う。

### 10.4 Phase 2 のバックエンド候補

同期はリアルタイムである必要がなく、試合後に自宅の通信環境で行えばよい。

| | Firestore | GAS＋スプレッドシート |
|---|---|---|
| オフライン対応 | 標準装備 | 自作が必要 |
| 学習コスト | 新規 | ほぼゼロ |
| データの可視性 | コンソールのみ | シートで直接確認・修正可能 |
| レスポンス | 速い | 数百ms〜数秒 |
| コスト | 無料枠で十分 | 無料 |

**推奨は Firestore。** オフライン同期を自作することがそのままデータ消失リスクになるため。GAS の利点（シートでの可視性）は Firestore からの書き出しで代替できるが、Firestore の利点は GAS では代替できない。

## 12. 設計原則

試作の過程で確定した原則。実装者が破りたくなる場面が必ず来るため明記する。

### 12.1 学童野球の頻度分布は一般論と異なる
外野ゴロ、内野からの長打、外野の落球はいずれも普通に起きる。**プロ野球の常識で「起こりにくい」と判断して選択肢を削らない。** 削った先が現場で必要になる。

### 12.2 選択肢の位置を文脈で変えない
打球位置によって結果の選択肢を出し分けると、押す場所が毎回変わり位置の記憶が効かない。**全ゾーンで同じ選択肢・同じ配置**とし、意味でグループ化する（出塁／アウト／その他）。選択肢が多いこと自体より、探す場所が変わることのほうが負荷が高い。

### 12.3 ボタンの文言はチームの記法規約に合わせる

**v0.2 までの原則を逆転させた。** それまでは「野球用語を使わない」とし、`野手選択` を「走者がアウト・打者は一塁へ」と表示していた。v0.3 では `記法規約.md` の語をそのまま画面に出す。

理由は、**記録者が最終的に書くのは紙の記法**であり、画面と紙で語が違えば対応づけを頭の中でやることになるため。用語が分からない記録者には、画面用の言い換えを覚えてもらうより、規約そのものを覚えてもらうほうが早い。画面が規約の練習台になる。

代償として、v0.2 §12.3 が守ろうとしていた「文言を見て意味が分からなければ不合格」は失われる。SC-01（事前レクチャーなしで記録し切れる）への影響は実戦で確認する（OPEN-12）。

データ上の名称（k）と画面表示（l）を分離して保持する仕組みは維持する。表示語が変わっても過去データが無効化されないためで、§8.5 の記法変換と同じ考え方である。

**呼び名は現場で使われているカタカナに揃える。** 守備位置は「一塁手」ではなく「ファースト」、
盤上の人は「走者」「打者」ではなく「ランナー」「バッター」とする。記法規約 §3 と §7 が
`ファースト` `ランナー1塁進塁` `4番バッター時ランナー進塁` と書いており、規約とも一致する。

**投球結果は「見逃しストライク」と「空振り」を分けた。** 規約が三振を K（見逃し三振）と SO（空振り三振）に書き分けるため、最後の投球の種別が要る。ボタンは1つ増えるが、押す回数は変わらない。

### 12.4 自由記述は保留のメモに限る
表記ゆれの排除が目的である以上、集計対象のデータに自由記述を許さない。保留のメモだけは例外とし、書式を問わない。

### 12.5 取り消しの単位は「利用者の1操作」
データ構造上の1イベントではなく、ボタン1押しを単位とする。誤操作の大半は確定前に起きるため、確定前の選択にも戻れることが必要。

### 12.6 記録を止めない
判断がつかない場面で入力が止まると、試合の進行から取り残されて記録全体が崩れる。**必ず先へ進める逃げ道（保留）を用意し、メモも必須にしない。**

### 12.7 盤面から分かることは聞かない
代打か代走か守備交代かは、その選手が塁上にいるか打席にいるかで決まる。**聞けば答えは得られるが、記録者の判断が入る余地を作ることになる。** 分かることは導出し、質問は本当に解釈が割れる場面（7.1 第3層）だけに使う。

### 12.8 履歴が残らない入力経路は塞ぐ
試合設定から打順を書き換えれば選手は入れ替わるが、交代の履歴は残らない。**目的は「同じ記録が残ること」であって「画面の表示が正しくなること」ではない。** 楽な抜け道があると必ずそちらが使われるため、経路自体を閉じる。

### 12.9 欠けている情報は、欠けていると表示する
旧データには守備位置がなく、投手が特定できない。ここで投球数を捨てるとデータが失われ、適当な投手に割り当てると誤った記録が残る。**「投手未設定」として保持し、画面で設定を促す。** 記録を落とすことと、嘘を書くことの、どちらも避ける。
