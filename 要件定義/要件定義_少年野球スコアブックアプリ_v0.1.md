# 少年野球スコアブックアプリ 要件定義書 v0.1

作成日: 2026-08-28
ステータス: ドラフト（Phase 1 のスコープ確定待ち）

---

## 1. 背景と目的

### 1.1 現状
- 少年野球チームのスコアは紙のスコアブックで運用している。
- 印刷された紙が正（原本）として保管・共有されている。
- 共有は記入済みページを写真に撮り、LINE で送っている。
- 集計欄（打率・投球数・チーム打撃率など）は試合後に手計算している。

### 1.2 課題
- **記録者によって書き方が揃わない。** 補殺・刺殺・失策の欄は埋める人と埋めない人がいる。判断に迷うプレー（失策か野選か、盗塁か暴投か捕逸か）の扱いが人によって異なる。
- 野球経験の少ない保護者が記録係に入ると、記録の質が大きく落ちる。
- 集計が手計算のため手間がかかり、間違いも起きる。
- 過去データが紙に閉じているため、傾向分析や対戦相手の対策に使えない。

### 1.3 目的
**誰が入力しても同じ品質・同じ表記の記録が残ること。**

成績集計の自動化はその副産物であり、主目的ではない。入力を正規化するためにルールエンジンを持つ、というのが本システムの中核方針である。

### 1.4 副次的な目的
- 投球数・出場イニングを試合中に可視化する
- 集計欄の自動算出により試合後の手計算をなくす
- 打球方向・配球・起用の傾向を後から分析できるようにする
- 対戦相手のデータを蓄積し、次回対戦時の対策に使う

## 2. 成功条件

本システムが成功したと判断する条件を以下に定義する。

| ID | 条件 |
|---|---|
| SC-01 | 野球経験の浅い保護者が、事前レクチャーなしで1試合を最後まで記録し切れる |
| SC-02 | 記録者が変わっても、同じ試合なら同じ記録になる |
| SC-03 | 出力したスコアブックが、現行の紙と同じ様式で印刷でき、そのまま保管できる |
| SC-04 | 1プレーあたりの入力が3タップ以内で完了する |
| SC-05 | 試合中に通信が切れても記録が継続でき、データが失われない |

## 3. 利用者と利用シーン

### 3.1 利用者
| 役割 | 想定 | 備考 |
|---|---|---|
| 記録係 | チームの誰でも（保護者・コーチ） | 野球知識のばらつきを前提とする。毎試合同じ人とは限らない |
| ベンチ（監督・コーチ） | 投球数・出場イニングの確認 | 入力はしない。画面を覗く |
| 分析者 | 試合後の振り返り | 現状は限られた人 |

### 3.2 利用シーン
- **試合中**：グラウンドのベンチ。スマホまたはタブレット1台で入力。通信環境は不安定または圏外。屋外のため画面が見づらく、片手操作になることもある。
- **試合直後**：スコアブックを印刷・PDF化して共有。
- **後日**：蓄積データから傾向を確認。

### 3.3 端末
- 入力：スマートフォン（最小幅375px想定）／タブレット
- 閲覧・修正：タブレット／PC
- **入力と閲覧で必要な画面が異なる。** スコアブック全面（27打席×2チーム）の俯瞰はスマホでは成立しないため、入力画面のみスマホ最適化し、俯瞰・修正画面はタブレット以上を前提とする。

## 4. スコープ

### 4.1 Phase 1（試作・実戦フィードバック取得）
入力UIの検証が目的。ここが使えなければ他の機能は意味を持たないため、最優先で作る。

- 自チーム・相手チームの選手／打順登録
- 1球ごとの投球結果入力（ボール／ストライク／ファウル）
- 打席結果の入力（ルールエンジンによる選択肢提示つき）
- 走者の進塁の自動導出と、例外時の選択肢提示
- イベント単位の取り消し（Undo）
- 投球数・出場イニングの画面表示
- 完全ローカル保存（IndexedDB）
- JSON によるエクスポート／インポート

### 4.2 Phase 2
- スコアブック様式の印刷出力（SVG）
- PDF／PNG 出力と共有
- サーバ同期と選手マスタ・相手チームマスタの共有
- 分析画面（打球方向、配球傾向、打順・起用の検証、対戦相手の傾向）

### 4.3 Phase 3 以降（未定）
- 個人成績の通年集計
- 複数端末からの同時入力
- 球種・コースの記録

### 4.4 やらないこと
| 項目 | 理由 |
|---|---|
| 球種の記録 | 学童では変化球がほぼなく、判別も記録者によってブレる |
| 投球コース（9分割） | 1球あたり1タップ増となり、リアルタイム入力の負荷が跳ね上がる |
| 試合中のリアルタイム複数端末同期 | 同時入力の要件がない。試合後同期で足りる |
| 投球数制限の警告通知 | 画面で見えれば十分との判断 |
| 自由記述による記録 | 表記ゆれの原因そのものであり、目的に反する。保留機能で代替する |

## 5. 機能要件

### 5.1 記録
| ID | 要件 |
|---|---|
| FR-01 | 1球ごとに投球結果（ボール／ストライク／ファウル）を記録できる |
| FR-02 | 打席結果を、その時点で発生し得る選択肢の中から選んで記録できる |
| FR-03 | 打球方向をダイヤモンド図のタップで記録できる |
| FR-04 | 走者の進塁はシステムが導出し、複数の解釈があり得る場合のみ利用者に問う |
| FR-05 | 判断がつかないプレーを「保留」として記録し、試合を止めずに進行できる |
| FR-06 | 保留した記録を試合後に一覧から確定できる |
| FR-07 | 直前のイベントを1件ずつ取り消せる |
| FR-08 | 選手交代・守備位置変更・代打・代走を記録できる |
| FR-09 | 1プレーごとに自動保存され、アプリが落ちても復帰できる |

### 5.2 チーム・選手
| ID | 要件 |
|---|---|
| FR-10 | 自チームの選手をマスタとして登録し、試合をまたいで再利用できる |
| FR-11 | 相手チームの選手を背番号のみで登録でき、氏名は任意とする |
| FR-12 | 相手チームもマスタとして蓄積し、次回対戦時に呼び出せる |
| FR-13 | 1つの打順枠に、人数の制限なく選手をぶら下げられる |
| FR-14 | リエントリー（再出場）を記録でき、出場可否の状態を管理する |

### 5.3 試合中の可視化
| ID | 要件 |
|---|---|
| FR-15 | 各投手の投球数を常時表示する |
| FR-16 | 各選手の出場イニング数を確認できる |
| FR-17 | 現在のイニング・アウト・走者・カウント・打者を常時表示する |

### 5.4 出力
| ID | 要件 |
|---|---|
| FR-18 | 現行の紙と同じ様式のスコアブックを生成し、A4で印刷できる |
| FR-19 | 同じ内容を PDF および PNG として出力し、共有できる |
| FR-20 | 集計欄（右端・最下部・投手成績表）をイベントから自動算出する |
| FR-21 | チーム独自の記法に合わせて記号を変換して出力できる |

### 5.5 分析
| ID | 要件 |
|---|---|
| FR-22 | 打球方向の分布を表示できる |
| FR-23 | 配球の傾向（初球ストライク率、カウント別の結果）を表示できる |
| FR-24 | 打順・起用の結果を検証できる |
| FR-25 | 対戦相手の傾向を過去試合から参照できる |

## 6. ドメインモデル

### 6.1 中核方針
**盤面の状態を保存せず、プレーイベントを追記のみで積み上げ、状態は畳み込みで導出する。**

この設計により以下が成立する。
- 取り消しがイベント1件の削除で済む
- ルールを修正した後、過去試合を再生して結果を再計算できる
- 同期時の競合がほぼ発生しない（過去を書き換えないため）

### 6.2 主要エンティティ

```
Game
  ├─ id, date, venue, weather, umpires[], scorerName
  ├─ rules: RuleConfig
  ├─ teams: { home: GameTeam, away: GameTeam }
  └─ events: PlayEvent[]        // 追記のみ

GameTeam
  ├─ teamId                      // マスタ参照
  ├─ isOwnTeam: boolean
  └─ lineup: LineupSlot[]        // 打順1〜9

LineupSlot
  ├─ order: 1..9
  └─ entries: LineupEntry[]      // 人数制限なし

LineupEntry
  ├─ playerId, position, enteredAtEvent, exitedAtEvent
  └─ entryType: 先発 | 代打 | 代走 | 守備交代 | リエントリー

Player
  ├─ id, teamId, uniformNumber
  ├─ name?                       // 相手チームは任意
  └─ battingSide?                // 打方

PlayEvent
  ├─ seq, timestamp
  ├─ inning, isTop
  ├─ battingTeam, batterId, pitcherId
  ├─ type: Pitch | PlayResult | Substitution | Other
  ├─ pitchResult?                // ボール/ストライク/ファウル
  ├─ playResult?                 // 安打/四球/三振/ゴロ/フライ/失策 ...
  ├─ hitZone?                    // 打球方向
  ├─ fielders?                   // 守備側の関与順（6-4-3 など）
  ├─ runnerMoves: RunnerMove[]
  ├─ outsMade
  └─ pending: boolean            // 保留フラグ

RunnerMove
  └─ playerId, from, to, reason  // 打撃/盗塁/暴投/捕逸/失策/野選/進塁打 ...
```

### 6.3 導出関数
```ts
applyEvent(state: GameState, event: PlayEvent): GameState   // 純粋関数
legalEvents(state: GameState): EventCandidate[]             // 選択肢の生成
deriveStats(events: PlayEvent[]): GameStats                 // 集計欄の算出
```

`applyEvent` と `legalEvents` を UI から独立させ、単体テスト可能にすることを設計上の必須要件とする。

## 7. ルールエンジン

### 7.1 3層構造

**第1層：制約（不正状態を許さない）**
- 同一塁に走者2人
- 走者の逆走
- 1イニング4アウト
- 打者結果が未確定のままのイニング終了

**第2層：導出（システムが自動で決める。利用者に判断させない）**
- 四球時の押し出し進塁
- 打者走者の一塁到達
- 打点の算出
- 犠打・犠飛の成立判定
- 打数から除外すべき打席の判定
- 補殺・刺殺・失策の記録

**第3層：質問（必ず選択肢で問う）**

ここが記録の揺れを吸収する本体である。
- 走者が進んだのは盗塁か、暴投か、捕逸か、野選か
- 失策の記録は誰につくか
- 振り逃げの扱い
- 打球が野手に触れた場合の安打／失策の判断

質問文は野球用語を使わず、状況の記述で提示する。
（例：「野選」ではなく「守備側が他の走者を狙い、打者は一塁に達した」）

### 7.2 設定値（RuleConfig）
連盟によって異なるため、ハードコードせず試合ごとの設定として保持する。

- 振り逃げの採用可否
- リエントリー（再出場）の可否と回数
- 1日／1試合の投球数上限
- 投手の登板イニング上限
- 規定イニング数、コールド条件、時間制限

## 8. 出力設計

### 8.1 単一SVGからの派生
スコアブック1枚を SVG として生成し、そこから全出力を派生させる。実装は「スコアブックSVGレンダラ」1つで足りる。

| 用途 | 実現方法 |
|---|---|
| 印刷 | SVG を A4 でブラウザ印刷 |
| LINE共有 | SVG を PNG 化（現行の写真共有と同じ使い勝手） |
| PDF | 同じ SVG を埋め込み |
| アプリ内閲覧 | 分析用に別レイアウト（縦スクロール）を用意 |

### 8.2 様式
- 使用しているスコアブックの製造元・様式が固定されているため、汎用化は不要。実寸に合わせたテンプレートを1つ作成する。
- **未記入ページのスキャンまたは真上からの撮影画像が必要**（目測では罫線が合わないため）。

### 8.3 印刷レイアウト上の課題
- 紙は1打順枠あたり3行しかないが、実運用では足りないことがある。
- 内部データは人数無制限で保持し、印刷時に3行へ収める。4人目以降は注記番号を振り欄外に送る方式を採る。

### 8.4 記法のマッピング
- イベントは標準形で保存する。
- 印刷時にチーム独自の記法へ変換するマッピングテーブルを設定として持つ。
- これにより記法が変わっても過去データが無効化されない。

### 8.5 個人情報
- 氏名は出力に含めるかを選択可能とする。
- 外部共有用の出力では、既定で背番号表示とする方針を検討する。

## 10. 技術構成

### 10.1 Phase 1
- Vite + React + TypeScript
- IndexedDB（Dexie）による永続化
- PWA
- **バックエンドなし。** 試作段階では入力UIの検証に集中し、同期は実装しない

### 10.2 Phase 2 のバックエンド候補

同期はリアルタイムである必要がなく、試合後に自宅の通信環境で行えばよい。

| | Firestore | GAS＋スプレッドシート |
|---|---|---|
| オフライン対応 | 標準装備 | 自作が必要 |
| 学習コスト | 新規 | ほぼゼロ |
| データの可視性 | コンソールのみ | シートで直接確認・修正可能 |
| レスポンス | 速い | 数百ms〜数秒 |
| コスト | 無料枠で十分 | 無料 |

**推奨は Firestore。** 理由は、オフライン同期を自作することがそのままデータ消失リスクになるため。GAS の利点（シートでの可視性）は Firestore からの書き出し機能で代替できるが、Firestore の利点は GAS では代替できない。

## 11. 段階リリース計画

| Phase | 内容 | 完了条件 |
|---|---|---|
| 0 | 記録画面のモック作成 | 過去試合の映像を見ながら入力を試し、タップ数を実測 |
| 1 | ローカル完結の記録アプリ | 1試合を最後まで記録できる。複数人に試してもらい意見を集める |
| 2 | 印刷・PDF出力、同期 | 紙と同じ様式で印刷でき、マスタを共有できる |
| 3 | 分析機能 | 打球方向・配球・起用・対戦相手の傾向を表示 |

**Phase 0 を飛ばさないこと。** 入力UIが実戦で成立しなければ、以降の実装はすべて無駄になる。
